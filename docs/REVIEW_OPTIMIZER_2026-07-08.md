## 1. 핵심 질문: 탐색인가 베끼기인가

**결론: 구조는 탐색이 맞다. 단, 전문가 시드가 이기는 요일(화·목)의 출력은 사실상 유저 로테의 복사본이고, 그것이 커밋 JSON→교차시드로 재주입되는 폐루프 때문에 오염이 영속·전파된다.**

### 1.2 판정

- **기어**: 진짜 탐색. 유저 빌드가 들어가는 경로 없음. 세트→메인→부옵→장신구를 프록시/풀시뮬로 자체 결정.
- **로테이션**: 빔은 매번 빈 상태에서 독립 탐색. 시드는 안전망(floor)일 뿐 빔을 지배하지 않음.
- **결정적 공백**: 시드를 **개량하는 메커니즘이 없다**. 빔 초기화에도 안 쓰이고 시드 근방 국소 탐색도 없어, 결과는 항상 `max(자체탐색, 시드 원본)`. 시드가 이기면 베낌, 지면 버림 — 둘을 섞어 유저를 넘어서는 경로가 없다.

### 1.3 검증 방법

`노교차시드` 인자 + `expertByDay` 비활성 상태로 전 요일 배치를 돌려 커밋 점수와 비교:
- 점수 동일/근접 요일 → 자력 도달 (시드는 무해한 안전망)
- 점수 하락 요일 → 시드 의존 (그 요일 출력은 유저 로테 복사본)

**판정: "베끼기"가 아니라 "자력 94.6% + 시드 보정 5.4%"다.** 처음 우려("정답지를 베끼는가")는 데이터로 반박된다.

- **기어·자리·진형은 100% 자력.** 목요일·일요일은 자력탐색의 진형·후열·자동로테 점수가 정식과 **동일**(목요일 자동로테는 자력이 오히려 3,488,627 > 정식 3,462,636). 격차는 오직 **로테이션 마지막 한 겹**이다 — 시드가 없으면 빔이 그 로테를 못 찾을 뿐, 빌드 전체를 베끼는 게 전혀 아니다.
- **전문가 로테가 등록된 화·목조차 자력이 정식의 91%.** 전문가 로테를 통째 복사하는 게 아니라, 빔이 자력으로 대부분을 재현하고 주입은 상단 ~9%만 채운다.
- **가장 의존적인 수요일(14.3%)은 전문가 로테가 없다** — 순수하게 교차시드(다른 프로필 로테)에 의존. 여기가 빔 자력탐색을 키워야 할 1순위.
- 금·토는 사실상 0% — 완전 자력.

→ 원래 목표("유저가 놓치는 이점 플레이를 스스로 발굴")를 이미 94.6% 달성. 남은 5.4%(특히 수요일·목요일)는 §1.2의 "결정적 공백"(시드 근방 변형 탐색 부재)을 메우면 자력으로 흡수 가능한 몫이다. S5에서 홀드제거 변형 시드를 넣은 게 그 첫 단추(월요일 정식이 자력 대비 +1.5%로 벌어진 것도 이 변형 덕).

## 2. 확인된 버그

### 장비 옵티마이저 (EquipmentOptimizer.cs)

#### E1. 2+2세트에서 한쪽 세트 보너스 통째 누락 ★최우선 [직접 교차확인 완료]
- `StatCalculationInput`(StatCalculator.cs:24–25)이 세트를 **1개만** 받는데, `ComputeStatResult`(EquipmentOptimizer.cs:579–589)가 `PieceCount` 최대 세트 하나만 넘김. 2+2면 둘 다 PieceCount=2라 먼저 열거된 무기 세트만 반영 → **방어구 쪽 2세트 효과 = 0**.
- 영향: 2+2 탐색공간 전체(GenerateAllCombinations 72개, BuildSetCombos n(n−1)개)가 체계적으로 저평가 → 실제 2+2 최적 캐릭터도 거의 항상 4세트로 결론.
- 시뮬레이터(BattleSimulator.cs:159–160)·SiegeBatchAllDays 등도 같은 단일 세트 입력 → 앱 전반의 구조적 이슈 (옵티마이저↔시뮬 일관성은 있으나 둘 다 틀림).
- 해결 재료: `EquipmentLoadout.GetTotalSetBonus()`(EquipmentLoadout.cs:67)가 이미 존재하나 미사용. `StatCalculationInput`에 다중 세트 전달 필요.

#### E2. 치확/약확 캡 언더슈트 — 100% 도달 원천 봉쇄
- `ExceedsCritWeakCap`(EquipmentOptimizer.cs:373–381)이 후보 티어 반영 후 합계 `>= 100`이면 무조건 거절 → 정확히 100 도달 배분조차 탈락, 치확 최대 96~99.x%에서 멈춤(부옵 1티어 = 치확 4/약확 5).
- 데미지 평가는 100 클램프 기댓값(DamageCalculator.cs:213·225)이라 96→100.8 티어도 +4%p 실가치가 있는데, 거절이 Score 비교 자체를 막아 회수 불가. 히트당 수 % 손실 가능.
- 수정 방향: 거절 조건을 "추가 **전** 이미 ≥100"으로 바꾸거나 Score 비교(클램프가 이미 한계효용 0 반영)에 맡김.

#### E3. 파티버프 floor의 MaxMerge 규칙 위반
- `PartyBuffCritWeak`(EquipmentOptimizer.cs:680–699)가 모든 아군·모든 스킬의 Cri/Wek를 무조건 합산. 게임 규칙(턴제끼리 같은 종류 MaxMerge)상 약확 54+27의 실효는 54인데 floor는 81로 과대 → E2 캡 거절이 조기 발동해 부옵 약확이 실수요보다 부족하게 세팅.
- 부수: 신규 `Effects`와 레거시 `PartyBuff`를 모두 합산(694–697행) — 양쪽에 같은 버프를 가진 캐릭터는 이중 계상(데이터 컨벤션 의존).

#### E4. 대표스킬 프록시가 타수 무시
- `EvaluateDamage`(714–717행)가 `Ratio` 최대 스킬 1개 선택. `Ratio`는 **타당** 배율(SkillDamage = DamagePerHit × AtkCount)이라 250×1타(총 250)가 150×3타(총 450)를 이겨 대표가 됨 → 캡 판정(`capSkill`)·메인옵 선택이 실전과 어긋날 수 있음. 도트·스택소모 캐릭터도 왜곡(도트는 치명 미적용인데 치확/치피 과대평가).
- 최소 개선: 선택 기준을 `Ratio × GetAtkCount` 총배율로.

#### E5. floor 미전달로 인한 목적함수 불일치 (조인트 경로)
- `OptimizeAccessoryJoint`(483·486행)와 `BuildSetCandidates`(169행)의 장신구 평가가 scorer=null일 때 `partyCritWeakFloor` 없이 계산 — 부옵은 floor로 최적화하고 장신구는 floor 없이 비교 → 캡 공급된 치확 장신구 과대평가 가능.

#### E6. 성능 낭비 (기능 영향 없음)
- (w1,w2)/(w2,w1)·(a1,a2)/(a2,a1) 순서쌍 중복 탐색(284–318행): 무기1/무기2 슬롯이 완전 동일하므로 ~2.2배 낭비.
- 2+2 (i,j)/(j,i) 중복(SetCombination.cs:41–54): 72개 중 36개 중복. **단 E1 수정 후에만 제거 안전** (현재는 둘이 다르게(잘못) 평가됨).
- 캡 체크가 후보마다 StatCalculator 풀계산 1회 추가(376행) — 치확/약확 후보는 매번 2회 풀계산.
- `TotalCombinationsSearched`(246행)가 실제 탐색량이 아니라 보관 결과 수(≤5)를 보고 — 표시용 필드 왜곡.

### 공성 옵티마이저 (SiegeOptimizer.cs / SiegeBatchAllDays)

#### S1. 사망 페널티가 파이프라인 절반에서 누락 ★최우선
- `AllyDeathPenalty` 기본값 0. 전달하는 곳은 `BuildSimConfig`(894행)뿐:
  - **진형·자리 전수탐색 config**(293–305행) 미전달 → 이 단계 `RankScore == TotalScore`, 사망 페널티 완전 무력화. "전멸 빌드 회피"가 자리/진형 선택에 전혀 작동 안 함.
  - **생존반지 평가 `SimBest`**(702–709행) 미전달 → ① 반지 채택(731행)이 raw 비교로 퇴화 — "딜 조금 깎고 생존 얻는 반지 채택" 의도(718–719행 주석)가 실제로는 불성립. ② 745–748행에서 무페널티 RankScore로 `best.BestRankScore`를 덮어씀 → 최종 후보 선정(485행)에서 **페널티 유/무가 섞인 비대칭 비교** — 사망 남은 반지-후처리 후보가 부당하게 이길 수 있음. ③ `ReoptimizeRotationAfterRings`(777–788행)의 기준점도 무페널티라 정당한 로테 재최적화가 차단될 수 있음.

#### S2. 좌표상승 롤백 시 `Character.ExclusiveWeapon` 미복원 — 상태 오염
- 1패스 스냅샷이 `t.Equipment`만 백업(175행)하는데 `SearchExclusiveWeapon=true`면 `EquipCandidates`가 공유 `Character` 객체의 조율을 변경(682·686행). 2패스 기각→1패스 채택 시(186–194행) 조율만 2패스 값 잔류 → 반환된 점수·로테가 재현 불가. 이후 feasibility 재생·JSON 점수가 최적화 시점과 다른 캐릭 상태에서 계산됨. 12초월 배치 기본 경로(`CoordinateAscentGear`+`SearchExclusiveWeapon` 동시 ON)에서 실제 발동.

#### S3. N시드 평균 vs 단일시드 비대칭 비교
- 빔 채택(429행)·교차수분(457행)은 `ScoreOnPlan`(N시드 평균, 866–878행)을 **단일시드 777·무페널티로 측정된** 자동로테 점수(308·321행)와 비교. 일요일(EvalSeeds=16)에서 시드 777이 자동로테에 유리하면 기대값상 더 나은 플랜이 기각되고, 최종 보고 점수도 단일시드 고점으로 남음(평균 정책 취지 위배). 빈 플랜을 평균으로 재평가하는 보정 경로 없음.

#### S4. 2패스 허수아비 후열 랭킹이 1패스 후열 플래그로 오염
- 후열 강제용 dummy DPS 루프(228–251행)가 `IsBackPosition`을 리셋하지 않음. 2패스에서는 직전 `EquipCandidates.FullScore`가 세팅한 1패스 후열 플래그가 잔류(580–582행) → 1패스 후열 멤버가 후열 공%를 받은 채 평가돼 구조적으로 유리 → 후열 선택이 1패스에 고착되는 자기강화 편향. 좌표상승 재탐색 취지와 충돌.

#### S5. `LoadRot`의 홀드 스텝 유실 (배치 툴)
- JSON `skillOrder`는 Hold 제외 저장(Program.cs:378), `LoadRot`(103–123행)은 전역 스킬턴 인덱스 기준 복원 → 원 플랜에 Hold가 있었으면 시드가 한 슬롯씩 밀린 다른 로테로 조용히 변형돼 주입됨. 크래시·점수 회귀는 없으나(교차평가 후보라 무회귀) "검증된 유효 로테" 시드 취지 훼손.

#### S6. 기타 구조적 리스크
- **빔 lookahead 1스텝**(RotationBeamSearch.cs:97–109): "셋업A→셋업B→버스트"처럼 보상이 2스텝 뒤인 라인은 부모가 프루닝될 수 있음(폭 10). 목요일 시드 +10% 사례의 유력 원인.
- lookahead 자식 시뮬 결과를 다음 깊이에서 재시뮬 — 시뮬 횟수 ~2–3배 낭비.
- `IsBetterPick`(eps=1.0 tie-break, 512–518행) vs 최종 선정 엄격 정렬(485행) 기준 불일치 + eps-비교 비추이성.
- `Optimize()`가 호출자 config의 `GearEval*`를 영구 변형(176–179행) — config 재사용 시 오염.
- `ScoreOnPlan` 평균 시 캐릭별 기여·라운드 점수는 시드 777 것 → 상세 합계 ≠ 보고 점수(표시 불일치, 주석으로 인지됨).
- 조합탐색(Candidates 사용) 시 기어 평가 팀이 FixedMembers+전체 Candidates(532행)로 5인 초과 — 실제 파티와 다른 버프 환경에서 세트 선정.
- 배치 툴 전문가 채택 비교(Program.cs:340–352): 전문가는 단일시드·`deathPenalty`, `res.BestScore`는 N시드 평균일 수 있음 — 현재 expert가 화·목(시드 1)뿐이라 미발현이나 인자 조합에 따라 즉시 발현되는 지뢰.
- `GearCompareSeed=777`이 배치 툴에 리터럴로 중복 — 상수 변경 시 재현성 어긋남. `_sim` 필드(151행)는 죽은 코드.

## 3. 권장 우선순위

1. **E1 (2+2 세트 누락)** — 탐색공간 8/9를 무의미하게 만드는 최대 버그. `StatCalculationInput` 다중 세트 지원 or `GetTotalSetBonus()` 경유. 시뮬레이터 쪽도 함께.
2. **S1 (사망 페널티 누락/비대칭)** — 채택 기준 정합성 문제라 다른 튜닝을 무의미하게 만들 수 있음. 모든 인라인 config에 페널티 전달 통일.
3. **E2 + E3 (캡 언더슈트 + floor 과대)** — 서로 반대 방향 오차로 결합돼 있어 같이 수정.
4. **S2 (조율 미복원)** — 스냅샷에 `ExclusiveWeapon` 포함.
5. **탐색 독립성**: `노교차시드`+expert OFF 대조 실행으로 요일별 자력 도달 측정 → 장기적으로 시드를 빔 초기 후보로 주입(시드 근방 변형 탐색)해 "유저를 이기는 빌드" 경로 확보. GearConstraints 화이트리스트도 주기적 전수 대조 필요.

수정 후에는 7요일 무회귀 검증 배치로 영향을 수치 확인할 것.

### 추가 발견 — 공성 기어가 2+2를 아예 탐색하지 않았음
E1을 고치는 과정에서, 공성 경로(`EquipCandidates` → `BuildSetCandidates` → `OptimizeForSetFull`)가 세트를 **문자열 이름**으로만 다루며 `Is4Set = true` 후보만 생성한다는 것을 발견했다. 즉 E1(2+2 스탯 계산 버그)을 고쳐도 공성 기어는 여전히 4세트만 보고 있었다 — 2+2는 계산이 틀린 게 아니라 **후보에조차 없었다**.

→ 세트 식별자를 `EquipSetConfig`로 승격하고 `BuildSetCombos`(4세트 + 2+2)를 후보 생성에 사용하도록 확장. 이제 딜러 허용 세트 4종 기준 후보가 4개(4세트) → 10개(4세트 4 + 2+2 6)로 늘어난다. "유저가 놓치는 이점 플레이 발굴"이라는 목표에 직결되는 탐색공간 확대다.

## 5. 검증 중 발견한 함정 2가지 (중요)

### T1. 커밋된 results/siege JSON은 stale — 현재 코드로 재현되지 않는다
`results/siege/*.json`의 점수는 **그 결과를 만든 시점의 코드**로 생성된 값이고, 이후 코드가 바뀌어도 재생성되지 않았다. 실측:

| 요일 | 커밋된 JSON | HEAD 코드 실제 재현값 |
|---|---|---|
| 월요일 | 9,643,644 | **8,934,488** |
| 금요일 | 7,103,046 | **12,776,816** |

→ **커밋된 점수를 기준선으로 삼으면 안 된다.** 이번 검수에서 이걸 모르고 커밋값과 비교하다가 존재하지 않는 "회귀"를 쫓아 ablation을 4번 헛돌렸다. 무회귀 검증은 반드시 `git stash` → HEAD 코드로 기준선 재생성 → 비교 순서로.
→ 별도 조치 필요: 코드 변경 시 결과 재생성을 강제하거나, JSON에 생성 커밋 해시를 기록해 stale 여부를 드러낼 것.

### T2. 교차시드의 경로 의존성 — 나쁜 실행 하나가 이후 실행을 오염시킨다
교차시드는 **가변 결과 파일**(`results/siege/*.json`)에서 읽는다. 중단된 실행·실험 설정·열화된 결과가 그 파일을 덮어쓰면, 이후 모든 실행이 그 나쁜 로테를 시드로 먹는다. 실측: 워킹트리의 `siege_월요일_12초월_윈디.json`이 6.03M(HEAD는 11.14M)짜리 열화본이었고, 이걸 시드로 쓴 실행에서 화요일 6,566,185 → HEAD 시드로 바꾸자 7,223,360으로 +10% 변동.
→ 조치 후보: 시드를 커밋된 최고 기록에서만 읽기 / 점수 하한 필터 / 시드 파일에 점수를 함께 저장해 회귀본은 무시.
